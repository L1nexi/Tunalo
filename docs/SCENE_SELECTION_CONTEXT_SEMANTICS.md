# 问题三：上下文语义与显著度

更新：2026-10-06。状态：讨论进行中。共同边界与设计原则见[讨论总览](SCENE_SELECTION_MODEL_DISCUSSION.md)。

本问题讨论怎样从原始观测构建雨、夜晚、工作等场景语义，使其能用于[变量预算和场景选择](SCENE_SELECTION_PROBABILITY_MODEL.md)。当前推进到活动观测，具体构建函数待讨论。

## 1. 现实锚定与数值表达

构建函数需要同时回答两个问题：

1. **现实感官锚定：**哪些现实状态或测量信息支持该语义，例如季节感、日内时间感、降雨量、持续活动？
2. **数值表达形式：**如何把这些依据映射为显著度，包括曲线、范围、连续性、不变量和尺度？

先锚定感知明确的状态，再近似中间区间。数值函数的选择应有现实依据。

### 构建函数的性质要求

| 性质 | 含义 |
| --- | --- |
| 跨变量可比较 | 不同上下文的显著程度能进入同一选择系统比较；这是最关键、也最难的要求。 |
| 保留绝对值 | 保留语义本身有多明显的信息，供尽力选择与候选比较使用。 |
| 独立于偏好和场景目录 | 语义由观测构建，包括理解当前活动所需的近期轨迹；用户偏好、场景数量和关联分布不改变语义值。 |
| 单调非减 | 其他相关条件不变，支持某语义的依据增强时，该语义的显著度不下降。 |

天气、活动、时段、季节可以使用不同的构建方式。

## 2. 有符号显著度与共同锚点

- 正向表示当前上下文对语义的支持。
- 零点表示语义中性或不存在。
- 负向表示反向关系；达到负向显著时，用于排除关联场景。

正负显著边界在曲线建模之后确定，显著不等于数值只要大于或小于零。

### 三类锚点

当前先寻找通常最显著的正向状态、零点和反向最显著状态。探索示例如下：

| 语义项 | 正向锚点示例 | 零点示例 | 反向锚点示例 |
| --- | --- | --- | --- |
| 夏季 | 盛夏最有夏天感的两三周 | 春季或春夏之交的位置待讨论 | 严冬最有冬天感的两三周 |
| 午夜 | 凌晨 1:00 左右 | 待讨论 | 13:00 左右 |
| 工作 | 一段时间持续工作 | 最初以空闲举例 | 一段时间持续娱乐 |
| 雨 | 暂以大雨为通常最显著状态 | 最初以阴天／多云举例 | 大晴天 |

各变量通常最显著的正向锚点暂以 1 作为共同参照。它允许更强状态超过，例如暴雨可以大于 1。这样从感官语义较明确的一端建立跨变量校准，再近似中间部分。

锚点的具体对应、负向范围、正负是否对称，以及变量内各语义项是否满足总和约束，仍待讨论。

### 负向依据明显违和

夏季与冬季有明确的反向关系；春夏之交的春季则未必违和。负向取决于感知上的违和，分类不同或另一个语义更贴切都不足以推出负向显著。

相邻季节、晴朗／阴云／降水、雨雪，以及工作／空闲／娱乐的关系，留待分别讨论。已确认的晴朗与雨、夏季与冬季的违和实例见问题二。

### 先建曲线，再定边界

显著度曲线先由感知依据构建，再讨论显著性边界 \(b\)。感知中的阈值效应描述上升速度变化，与召回的硬边界是两件事。

曲线连续性、正负边界是否对称，以及问题二探索过的评分交接点 \(a\) 是否有必要，仍待讨论。

### 显著度与判断把握

可以很确定正在下小雨，同时给出低显著度；活动则需要合成一段时间的观测。判断把握与显著度有区别，但用户质疑把握程度作为统一独立维度的价值。

信息缺失、无法判断、语义不存在与成立但不显著，是否需要分别表示仍待讨论。无法识别的活动与空闲应分别理解。

## 3. 时段与季节的曲线方向

季节按春、夏、秋、冬讨论；时段曾以白天、黄昏、午夜、凌晨举例。季节可利用对称性探索共用函数结构，时段划分待讨论。

一次非正式访谈提供了启发：夏季感可以来自海边经历，冬季感也受凉到冷、降温降雨等变化影响。季节感除了日期，还可能受环境变化和生活经历影响。

当前认可的曲线方向是：时段与季节显著度的上升段主要由平缓上升和快速上升组成。感知存在阈值效应，季节感可能长期变化缓慢，某几天的天气变化则提供更强依据。具体近似函数待讨论。

支持依据增强时，显著度保持单调非减；仅因习惯而回落的方案未被接受。快速上升可以用连续曲线表达。

各项锚点与中间段，以及气温、体感温度、日出日落怎样与日历和时钟结合，仍待讨论。

## 4. 天气数据与语义

### 数据来源

当前选择以 OpenWeatherMap（OWM）为主。此前考虑过 Open-Meteo 免 API Key、遇到公网 IP 共享限制再补 OWM；查阅文档后转向 OWM，理由是文档与现有信息更适合当前工作。和风天气的国内可达性曾被考虑，但本次注册体验和接入方式不适合独立桌面工具的需求。

接口事实见[OpenWeather 当前天气 API](archived/reference/OPENWEATHER_CURRENT_API.md)：

| 数据 | 语义用途 |
| --- | --- |
| 天气现象与代码 | 支持晴朗、阴云、降水及细分现象判断 |
| 降雨量、降雪降水量 | 支持降水强度锚定 |
| 气温、体感温度 | 辅助季节语义；`temp_min/max` 表示当前温度范围，详见参考文档 |
| 日出、日落 | 辅助时段语义 |

同一数据来源可以支持多个上下文变量。

### 降雨强度锚定

用户认可参考气象雨量分级中各档量级扩大的特点，提出以下显著度示意：

| 降雨等级 | 显著度示意 |
| --- | --- |
| 小雨 | 0.25 |
| 中雨 | 0.5 |
| 大雨 | 1.0 |
| 暴雨 | 2.0 |

这些值表达增长方向，具体曲线待讨论。以实际雨量为横轴时，需要结合各档物理范围判断映射尺度；等级值按倍数增长本身不足以确定采用对数函数。

气象分级的累计时段与 OWM 字段的单位需要对齐。连续雨量与类别怎样结合、暴雨以上怎样延伸，以及雨雪混合怎样映射强度，仍待讨论。

### 晴朗、阴云、降水与雨雪

当前认可保留晴朗、阴云，并以降水组织共同语义，内部区分雨和雪。层次组织用于共享推导，减少为每个语义项独立映射全部天气代码的复杂度。

雨与雪分别保留可关联的场景。用户希望同一播单承接雨雪时，可以将两个场景绑定同一 Playlist。

雨雪混合可以同时支持雨和雪；预算主体仍是天气这一粗变量。具体强度、相邻项的支持与负向关系，以及雷暴、雾霾等现象如何映射到有限语义项，仍待讨论。

## 5. 活动观测与桌面窗口池轨迹

活动通过观察与推断形成，当前先评估能区分工作、空闲、娱乐的信息。瞬时窗口状态需要合成为一段时间的活动语义。

### 信息来源的取舍

| 信息来源 | 当前判断 |
| --- | --- |
| 前台应用与窗口 | 重要线索；应用身份、标题及变化通常能反映注意力所在。 |
| 非前台桌面窗口 | 值得挖掘，与前台历史串联成桌面窗口池轨迹。 |
| 普通后台进程 | 价值不足；运行本身难以反映用户正在参与的活动。 |
| 窗口呈现状态 | 全屏、最大化等单独区分能力有限，作为轨迹辅助信息的价值待评估。 |
| 输入活动 | 区分度不足；无输入也可能是阅读、思考或观看。 |
| 媒体播放与音频 | 工作、空闲、娱乐都可能伴随音乐；视频名等信息的边际收益也可能较低。 |
| 系统会话状态 | 锁屏、解锁等活动分类信号较弱，当前不作为重点。 |
| UI Automation、界面内容与画面识别 | 投入产出比低，并有越过产品观察边界的感觉，当前不展开。 |

浏览器扩展、网址等深入集成曾被提及，当前路线未采用。

### 当前探索路线

维护可观察的桌面应用窗口池，串联前台与非前台窗口历史。[窗口枚举](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-enumwindows)与[窗口事件](https://learn.microsoft.com/en-us/windows/win32/winauto/event-constants)提供技术依据。

待评估的观察内容包括：

- 窗口池组成：持续存在、出现和关闭。
- 每个窗口的前台历史：切入、停留、离开、反复返回。
- 窗口间切换：近期反复往返的对象与偶尔经过的窗口。
- 呈现状态变化：展开、最小化、位置和大小。

路线的价值假设是，应用使用关系能为单个窗口提供活动背景。例如：

- 编辑器 → 浏览器 → 终端 → 编辑器 → 浏览器。
- 游戏 → 浏览器 → 游戏 → 聊天窗口 → 游戏。

两个轨迹都有浏览器，但周围的应用与反复返回的对象不同，可能形成不同活动依据。多个窗口也可以服务于同一活动。

持续存在与近期持续参与活动需要分别理解。编辑器挂着一整天，与反复离开又返回提供的证据不同；单个窗口停留很久，也可能仍有活动性质上的歧义。

怎样从轨迹识别活动并形成显著度，采样周期、历史长度和状态更新方式，仍待讨论。

## 6. 待讨论

- 各变量的具体锚点、输入依据、构建函数及中间曲线近似。
- 跨变量校准与绝对值含义，数值范围、连续性和不变量。
- 相邻语义的中性、支持和反向关系。
- 曲线确定后的正负显著边界，以及同一变量内多个语义项怎样共同决定变量预算。
- 天气代码与定量雨雪数据到有限语义项的映射。
- 窗口池轨迹到工作、空闲、娱乐显著度的推断。
- 缺失信息、无法判断与语义中性的表示，以及是否单独建模判断把握。
