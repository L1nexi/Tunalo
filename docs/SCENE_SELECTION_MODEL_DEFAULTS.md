# 场景选择模型：构建参数及规则表

日期：2026-10-09。状态：供实施使用的第一版内部取值；尚未实现，也不声称已完成真实使用校准。

本文落实 [SPEC](SCENE_SELECTION_MODEL_SPEC.md) 的内部参数、活动识别、天气映射和 Scene 关联。用户已经确定行为边界，并授权实施者拟定这些数值与规则；它们不进入用户设置，也不需要逐项转成产品问卷。后续调整须保留 SPEC 的验收行为。

## 1. 内部初始参数

| 参数 | 初值 | 依据 |
| --- | --- | --- |
| 正向边界 `b` | 0.5 | 中等支持开始参与显著召回，等于边界算显著 |
| 负向边界幅度 `b_-` | 0.5 | 初版对称，等于负边界开始排除；数据结构不强制正负相等 |
| 变量温度 `T_V` | 1.4 | 靠近 M-05 允许的上界 `1/ln(2) ≈ 1.442695`，兼顾该例排序和探索 |
| 场景温度 `T_C` | 1.5 | 相比温度 1 更平缓；同一候选集中两场景评分相差 1 时，概率约为 0.660756／0.339244 |
| 活动窗口 `N` | 600 槽 | 每次现有采样推进一槽，不要求严格十分钟 |
| 活动年龄尺度 `h` | 300 槽 | 年龄 300 的权重为 0.5，窗口末端权重约为 0.004；近期观察优先，仍保留较早方向 |
| 活动映射 `q` | 0.5 | 净方向约 0.5 时输出约 0.502，保留初段平缓和后段趋缓 |
| 季节、时段插值 `q` | 各为 0.5 | 采用同一初始形状；仍是独立参数，不与活动强制绑定 |
| 季节峰值 | 春 80、夏 172、秋 265、冬 355 | 沿用原代码的年内日期与 365 日周期 |
| 季节平台半宽 | 10 日 | 每个语义在本季峰值附近为 1、相对季节附近为 -1，相邻季节附近为 0 |
| 时段平台 | 无 | 沿用真实峰值与虚拟时间换算，仅以 S 形曲线连接锚点 |

M-05 在 `T_V=1.4` 时，雨天概率为 `0.5052844367`，日间工作为 `0.4947155633`。它保留暴雨的优势，但不会把分布集中到单一场景。这是指定参数下的算例；算法测试可以显式采用该参数并核对概率，产品默认参数校准后不要求保持这组数值，仍须满足 SPEC 的排序与模型约束。

### 活动窗口与逐渐建立显著度

计算上把未观察部分视为零，按最新至最旧记为 600 个逻辑槽位；这不要求实际存储一个填满零的数组。取 `h=300` 时，年龄权重为 `w[a] = 2 ** (-(a/300) ** 3)`，固定分母约为 `303.0764592049`。每次新观测只计入一次，只考虑最近 600 次观测；不使用“已观察数量”作为分母，也不以求值调用次数推进历史。

显式取 `N=600`、`h=300`、`q=0.5`，从未观察状态开始持续观察工作，算例为：

| 已观察槽数 | 工作净方向 | 工作显著度 |
| --- | --- | --- |
| 0 | 0 | 0 |
| 1 | 0.003299497 | 约 0.000000200 |
| 60 | 0.197704883 | 0.042110997 |
| 120 | 0.391674959 | 0.284477721 |
| 180 | 0.572826991 | 0.649890150 |
| 300 | 0.848278244 | 0.969903586 |
| 600 | 1 | 1 |

这些槽数不是额外等待阈值。没有新观测时不推进，不按经过的墙上时间补槽；读取结果或诊断也不推进。可用有界方向存储和预计算权重实现，具体容器、缓存与遍历方式不构成验收要求。

表中的净方向和分母用于解释算例，不要求成为公开接口或 Tick History 字段。数值对照测试固定上述参数后检查最终显著度；实际默认参数另按 SPEC 验证逐渐建立显著度、反对称和满窗口锚点。诊断字段按实际用途选择，算法测试不通过诊断读取中间量；每条 Tick History 不复制完整活动窗口。

## 2. 季节与时段的具体构建

季节沿用 `SeasonPolicy` 的日期输入。对每个季节语义，四个峰值处依次指定本位 `1`、两个邻位 `0`、相对位 `-1`；每个锚点前后各 10 日保持该值。相邻平台的尾端与下一平台的首端之间按 SPEC 的 `f_q` 插值，最后一个平台与次年首个平台同样衔接。只要求数值连续和各过渡段单调，不新增导数连续约束。

TimePolicy 复用 `_compute_peaks`、`_warp_time` 和 `_update_from_context` 的现有逻辑：天气 API 的时间戳按原路径转换为当地时间；日出、白昼中点、日落、夜间中点分别对齐 `dawn/day/sunset/night`。只有虚拟时间的相邻峰值相距 6 小时。对每个语义，在本位、邻位、相对位给出 `1/0/-1`，峰值之间直接插值，不截出平台。

日出日落未变化到原代码的更新阈值时复用峰值；缺失时保留已有峰值，初始没有峰值则全零。配置替换仍按原代码重建 TimePolicy，不新增峰值持久化或状态转移。

## 3. 第一版内置活动规则

只使用当前前台窗口。沿用原识别器的标准化及优先级：标题优先于进程，精确优先于正则优先于包含，再比较字面长度与声明顺序。以下进程均为去掉 `.exe` 后、不区分大小写的精确匹配；标题为不区分大小写的包含匹配。首版不需要正则规则。

| 规则来源 | 方向 | 内置模式 |
| --- | --- | --- |
| 编辑器与开发工具进程 | 工作 `focus` | `code`、`cursor`、`windsurf`、`devenv`、`idea64`、`pycharm64`、`webstorm64`、`rider64`、`goland64`、`clion64`、`datagrip64`、`studio64`、`sublime_text`、`notepad++` |
| 文档与笔记进程 | 工作 `focus` | `winword`、`excel`、`powerpnt`、`onenote`、`wps`、`et`、`wpp`、`obsidian`、`notion` |
| 创作工具进程 | 工作 `focus` | `figma`、`photoshop`、`illustrator`、`blender` |
| 播放器与音乐进程 | 娱乐 `chill` | `vlc`、`mpv`、`potplayer`、`potplayer64`、`spotify`、`cloudmusic`、`qqmusic`、`foobar2000`、`wmplayer` |
| 常见游戏进程 | 娱乐 `chill` | `dota2`、`cs2`、`league of legends`、`valorant-win64-shipping`、`hades`、`hollow_knight`、`stardew valley`、`terraria` |
| 开发、文档与创作页面标题 | 工作 `focus` | `Visual Studio Code`、`GitHub`、`GitLab`、`Stack Overflow`、`飞书文档`、`腾讯文档`、`Google Docs`、`Google Sheets`、`Figma`、`Notion` |
| 视频与直播页面标题 | 娱乐 `chill` | `YouTube`、`哔哩哔哩`、`bilibili`、`腾讯视频`、`爱奇艺`、`优酷`、`Netflix`、`Twitch`、`斗鱼直播`、`虎牙直播` |

这是一版粗分类：创作和文档处理归入工作方向，不判断是否用于职业；视频页面归入娱乐方向，不推断内容是否教学。规则命中仅提供一个观察槽的方向，短暂误分类不会被直接归一成完整活动。

浏览器、聊天软件、终端、文件管理器和游戏启动器不单凭进程归类。例如 `chrome/msedge/firefox/brave`、`wechat/qq/discord`、`windowsterminal`、`explorer`、`steam/wegame` 仍须有明确标题规则，否则为 OTHER。空窗口、未知进程且标题未命中也为 OTHER；不由空闲时间、后台播放或后台进程补推活动。

旧 Profile 的活动规则和编辑入口直接删除，不导入、不合并、不提供覆盖机制。常用应用清单由产品代码维护；后续遇到误判时调整这张表，不增加另一套用户规则系统。
