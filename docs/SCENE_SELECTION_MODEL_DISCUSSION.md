# 场景选择模型：偏好、概率预算与上下文语义讨论

记录始于：2026-10-04。更新：2026-10-05。

状态：讨论进行中。本文记录问题一、问题二的讨论进展，包括已确认的负向影响与场景选择约束实例，并作为问题三的讨论入口。已确认的产品边界、当前采用的机制方向、探索过的方案和未确认的行为草案分别列出；本文不是新算法的实现规格。

起点见 [产品定位](PRODUCT_POSITIONING.md) 与 [场景模型重审及中立基准 ADR](adr/0002-scene-model-rethink-and-neutral-baseline.md)。该 ADR 确认了重审方向与中立参照，本文继续讨论新的用户偏好和场景选择机制。具体算法仍需在上下文语义得到澄清后设计。

## 1. 讨论范围与方式

最初提出的三个问题是：

1. 什么是用户偏好？用户有哪些偏好？用户以哪种方式表达偏好更为自然，我们应当允许用户以哪些方式表达偏好？
2. 如何根据当下信息、当下系统状态、用户偏好和可用场景表，输出场景选择并更新系统？另需讨论场景如何与一个或多个上下文变量关联。
3. 原始传感信息不具有场景层面的语义。如何根据当下信息构建场景层面的语义？对构建函数应该提出哪些性质要求，使其可以作为系统进行选择的输出，例如跨变量可比性、变量内的单调非减性？

问题一、问题二的讨论内容已记录，2026-10-05 补充了问题二的约束实例。问题二仍有开放部分，问题三尚未展开。

讨论方式由用户明确要求：

- 不复述用户已经表达清楚的意思。解释仅在需要确认理解时使用。
- 以产品与系统设计为主。机制未形成之前，不提前进入细节；允许的算法探索也不能被擅自升级为定案。
- 助手应补充遗漏、加强设计，或质疑不合理、不完备之处。
- 决定和讨论的收束由用户负责。

## 2. 已确认的产品边界

### 2.1 Scene 与 Playlist 解耦

项目负责根据上下文判断、选择当前应采用的 Scene。用户通过给 Scene 绑定 Wallpaper Engine Playlist，决定这个场景下希望看到的内容。

场景选择不等于判断用户此刻想看哪张壁纸，也不接管 Playlist 的审美与内容组织。

### 2.2 偏好面向习惯与中长期倾向

系统处理习惯或中长期偏好，不预测临时意愿。用户产生临时意愿时，可以通过 Wallpaper Engine 入口调整。

系统不要求用户频繁声明状态，不通过反馈训练一个学习式推荐系统。免打扰属于设计初衷。

### 2.3 上下文语义独立于偏好

雨、夜晚、工作等上下文语义的构建，应独立于用户偏好。选择哪些场景来响应这些事实，才涉及用户偏好。

这里的“事实”不预先保证传感与推断一定正确；传感信息如何支持语义判断，属于问题三。

### 2.4 模糊的正确胜过精确的错误

在用户对某个上下文感知最明显的时候，系统需要最佳的正确性；在感知不明显的时候，允许犯错。系统需要正确理解的显著情境，通常也更容易被理解；容易理解错的情境，通常本身较模糊，用户也更能接受近似选择。

小雨与暴雨、初夏与盛夏的例子用于说明这一关系，不是直接定义天气或季节的优先级。模型不追求永远理解用户，而是在显著情境中可靠地响应，在模糊情境中允许无伤大雅的选择差异。概率选择也可以给某些候选零概率；随机性本身不是在明确情境下保留错误选择机会的理由。

### 2.5 中立参照

中立参照的必要前提包括：四个上下文策略均处于各自的显著参照时刻；各自只有一个主导语义项；存在四个对应的简单场景；没有额外偏好。

这个对称参照下，四个简单场景各以四分之一概率被选中。参照条件中的“显著”不能省略。

该参照不要求所有真实候选池均匀选择，也不把“无显著变量”与中立参照视为同一种情况。普通情境中的显著度可以不同，显著参照也不是上限，暴风雨等情境可以更强。

## 3. 问题一：用户偏好

### 3.1 粗粒度倾向与关系

讨论主线中的偏好面向天气、活动、时段、季节等上下文变量。例如，希望壁纸跟随季节、当日时间或工作／休闲。

用户可以对变量表达同等偏好，也可以表达先后关系。讨论不要求用户理解内部权重或校准数值。

“新增一个偏好”只是从单变量推导多变量行为的分析方式，不代表产品配置流程或用户操作语义。

### 3.2 单变量与多变量的行为

单变量偏好中，偏好变量显著时，主要采用与它关联的场景；不显著时，退回中立选择。这里“希望跟随季节”的完整含义，是希望系统在季节具备显著性时跟随季节，过渡期的近似选择可以接受。

多变量偏好中：

- 同一偏好地位的变量，只有一个显著时，采用它对应的场景范围；多个同时显著时，将它们关联的场景合入候选池。
- 不同偏好地位的变量，优先考虑更高偏好层级中显著的变量；该层没有显著变量，再考虑下一层。
- 偏好变量均不显著时，退回中立选择。

显著性保证有关场景进入候选范围，不保证某个场景最终获得正概率或一定被选中。同一偏好层级的候选也不必等概率，因为当前显著程度可以不同，其他关联也可能受到当前上下文的负向影响。

### 3.3 级联式、启发式的偏好表达

当前采用的方向是按偏好程度从高到低扫描：

1. 查看当前偏好层级。
2. 若其中有显著变量，将这些变量关联的场景加入候选池，并停止向更低层级扫描。
3. 若该层级没有显著变量，查看下一层级。
4. 若所有已表达偏好都未提供显著变量，回到中立选择。

偏好首先影响候选范围，池内选择另行讨论。“召回”和“重排”用于帮助区分这两项职责，不预设现成推荐架构。

### 3.4 负向意愿与配置一致性

是否需要独立的负向意愿表达，尚未决定。在变量全集已知时，“不希望跟随天气”可以用正向偏好其他变量表达，也可以通过不启用天气相关场景体现。

明确表达偏好却没有启用相应场景，被用户视为配置矛盾，可在配置层提醒。这与后文“本轮某个变量没有候选场景”的运行时可用性处理，需要分别理解。

第 4.4 节的上下文负向影响来自当前语义与场景关联之间的关系，不依赖用户表达负向意愿。

### 3.5 细粒度偏好的额外语义与代价

粗粒度“活动”表达隐含工作、休闲等内部语义项具有相同偏好地位。细粒度表达只有在这些内部项与其他变量具有不同偏好关系时，才提供额外信息，例如：

- 工作低于天气，天气低于休闲。
- 白天低于工作，工作低于夜晚。

仅有工作低于休闲，通常没有额外选择作用，因为同一粗变量内部的这些语义项通常不会同时显著。外部变量与内部项之间的等于关系也可能提供差异，例如工作低于休闲，休闲等于天气。

用户判断这种跨变量细分偏好属于长尾需求：从四个粗变量扩展到十余个内部项，会显著增加表达和配置复杂度，并使用户需要理解系统的内部分类。是否支持细粒度表达、是否混合粗细粒度、具体配置方式，尚未定案。

## 4. 问题二：场景召回与生态位

### 4.1 基本对象

选择过程接受上下文的数值显著度、候选场景及其关联，输出场景或场景选择分布。布尔显著性不足以表达池内比较所需的强弱。

天气、活动、时段、季节是上下文变量；雨、工作、白天、夏季等是这些变量下的具体语义项。讨论中的场景关联示例包括：

| 场景     | 关联语义项 |
| -------- | ---------- |
| 雨天     | 雨         |
| 日间工作 | 白天、工作 |
| 雨天工作 | 雨、工作   |

关联的最终表示方式、粗变量与具体语义项的数值关系，仍需结合问题三讨论。上述集合只是说明语义关系，不是已确认的数据结构。

### 4.2 采用并集召回方向

候选召回采用并集方向：场景关联了本轮参与召回的某个显著上下文，就可以进入候选池；不要求其全部关联都显著。

例如：

- 雨显著：雨天、雨天工作可以进入候选池。
- 工作显著：日间工作、雨天工作可以进入候选池。
- 雨、工作同时参与召回：这三种场景都可以进入候选池。
- 没有显著变量：召回全体可用场景，进行尽力选择。

曾探索按关联重叠数量从高到低查找、找到后停止的方式。它会让场景表的组合覆盖影响哪些显著上下文还能参与选择：暴雨、工作、夏季都显著，但只有雨天和夏季工作场景时，最高重叠召回会排除雨天，即使暴雨最显著。用户认可这一问题，转向简单并集召回。

至少一个显著关联，为场景参与比较提供了理由；最终选择还需考虑其余关联与当前上下文是否一致。一个关联得到支持，不能保证整个场景都是可以接受的选择。

继续沿用并集召回。进入候选池的场景可以在条件分配中获得零概率；负向影响不要求把召回改成“所有关联都必须显著”。

### 4.3 单一与复合场景的生态位

雨天与雨天工作应占据不同生态位：

- 雨显著、工作支持弱时，更倾向雨天。
- 雨和工作都明显时，更倾向雨天工作。

两种情况都会召回这两个场景，差异由池内选择体现。这个关系不意味着所有复合场景都优先于简单场景。

当前选择行为的检验例子还包括：

- 雨和夏季都显著时，两个单项场景之间更倾向显著度较高者。
- 暴雨非常显著，工作、白天普通显著时，不能仅因日间工作关联两项，就让它胜过雨天。
- 不存在显著变量时，在候选池内进行尽力选择。

本节上述例子描述倾向，不要求在显著性边界处发生严格的胜负翻转。第 4.5 节另外记录了具体候选组合下的零概率约束。

### 4.4 语义关系与负向影响

场景被某个显著关联召回，不意味着当前上下文与它的所有关联都是同一个方向。夏季显著可以支持夏季工作，也可以抑制冬季工作。

语义项之间的关系需要被考虑。夜晚、雨天与季节接近正交；春季、夏季、冬季则属于同一变量内部的相关语义，其中夏季与冬季有明显的反向关系。具体怎样表达这些关系，留待问题三讨论。

只读取场景自身关联项的显著度，信息可能不够。例如，“工作高、冬季低”既可能出现在季节整体模糊时，也可能出现在夏季非常明显时。后者的负向影响来自场景没有关联的夏季及其与冬季的关系。即使没有夏季工作这个候选，明显的夏季仍应影响冬季工作的选择机会。

需要区分两类行为：

- 明确相反的关联，可以构成零概率的理由，具体已确认实例见第 4.5 节。
- 未表达某个上下文，或额外关联支持不足，可以影响相对概率，但不因此自动归零。夏季工作没有表达天气，暴雨本身不会让它变成与天气相反的场景。

这些关系服务于场景语义的比较，不涉及判断 Playlist 的具体壁纸内容。

### 4.5 已确认的约束实例

以下实例均无额外偏好；“活跃”按当前讨论中的显著情境理解。它们约束选择行为，尚不规定具体计算函数或语义表示。

#### 4.5.1 夏季工作与冬季工作

候选仅包含夏季工作与冬季工作，当前夏季、工作均显著：

- 夏季工作的选择概率为 100%。
- 冬季工作的选择概率为 0。

两个场景同样响应工作，夏季工作还符合当前明显的季节，冬季工作则具有明确相反的季节关联。冬季工作不能仅因共同的工作关联继续获得选择机会。季节预算由夏季工作承接，活动预算在这两个候选之间分配时也应全部交给夏季工作。

冬季工作仍可通过工作关联进入候选池，再在条件分配中获得零概率。这个实例确定的是该候选组合下的结果；尚未据此确立“只要夏季显著，所有带冬季关联的场景一律排除”的通用规则。

#### 4.5.2 夏季工作、工作与雨天工作

候选包含夏季工作、工作、雨天工作，当前夏季、工作均显著。分别考虑晴朗、雨天、暴雨显著；暴雨这一行假设天气比当前夏季更显著。

| 当前天气 | 夏季工作 | 工作 | 雨天工作 |
| -------- | -------- | ---- | -------- |
| 晴朗显著 | 主要选择 | 较低概率 | 概率为 0 |
| 雨天显著 | 与雨天工作共同成为主要选择 | 低于两个复合场景 | 与夏季工作的相对概率取决于显著度 |
| 暴雨显著 | 仍然合理，但低于雨天工作 | 低于两个复合场景 | 明显占优 |

晴朗显著时，雨天工作含有明确相反的天气关联，选择概率为零。夏季工作与工作都成立，夏季工作额外响应了显著的夏季，因此更值得选择。没有晴朗场景承接天气预算，不妨碍晴朗语义参与活动预算内部的场景比较。

雨天显著时，夏季工作与雨天工作分别响应工作之外的一个显著上下文，彼此没有冲突。夏季与雨天同等显著时，两个复合场景应对称；哪个更显著，就更倾向相应场景。

暴雨比夏季更显著时，雨天工作应明显占优。夏季工作没有表达天气，仍然合理，不应仅凭暴雨就归零。

通用的工作场景退居较低概率，不因存在更贴切的复合场景就被要求归零。它的生态位是：其他上下文模糊时更有优势，其他上下文明显时让出更多选择机会。除明确给出的零概率与 100% 外，具体概率尚未确定。

## 5. 问题二：概率模型探索及转向原因

### 5.1 逐场景评分是探索方案

曾探索以场景关联项求和：

\[
G(c)=\sum_{i\in A_c}(s_i-b)
\]

其中 \(b\) 是显著性边界，不能预先固定为 1。最初的确定性方案还用显著关联数量处理边界同分，随后探索将得分通过 softmax 转成概率：

\[
P(c)=\frac{\exp(G(c)/T)}{\sum_{d\in C}\exp(G(d)/T)}
\]

评分中的交接点也可以另设为 \(a\)，与召回的边界 \(b\) 分离。\(a\)、\(b\)、\(T\)、求和方式及边界处理均未定案；该方案不应被当成当前已选算法。

用户要求停止固化这一路线，并借助 `codebase-design` 中的 `DESIGN-IT-TWICE` 探索不同概率机制。

### 5.2 三条概率机制的比较

| 探索方向             | 概率的含义                               | 主要讨论所得                                                                                         |
| -------------------- | ---------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| 全局上下文覆盖       | 直接求场景分布，使各上下文的覆盖接近目标 | 复合场景同时贡献多个覆盖；新增单项场景后，复合概率可能下降。整体覆盖与当下场景生态位并非同一个目标。 |
| 上下文来源的层级分配 | 先决定响应哪个变量，再条件选择场景       | 可以先保留上下文的响应份额，再由场景承接；复合场景可以汇集多个来源。                                 |
| 共享随机上下文的竞赛 | 随机化响应力度，让场景共享随机量并竞争   | 场景重叠参与概率生成；具体版本仍有加法、关联成本、波动和弱信号处理等假设。                           |

这些方案用于比较机制，不表示三者均已获采纳或正式否决。当前方向部分吸收第二条；其余具体计算不随之成为已确认设计。

### 5.3 多场景暴露出的数量偏置

用户提出：候选有春季工作、夏季工作、秋季工作、冬季工作，以及雨天工作。

- 只有工作明显、其他关联支持相近时，五个工作场景均匀选择可以接受。
- 雨和工作同等明显时，雨天工作可能更贴切，但逐场景归一化会让四个季节工作合计占据较大份额。

设雨天工作比每个季节工作高 \(\Delta\) 分，其概率倍数为 \(k=\exp(\Delta/T)\)，则：

\[
P(\text{雨天工作})=\frac{k}{4+k}
\]

场景目录的细分程度由此影响对上下文的综合响应。这个例子里所有场景均关联两项，公共工作贡献与相同的关联成本会抵消，改变 \(a/b\) 不能消除数量因素。

固定给季节侧按数量补偿也不足以满足两个状态：它可能改变仅有工作明显时原本合理的均匀选择。需要稳定的是上下文获得的响应机会，场景层再决定如何完成响应。

## 6. 当前方向：先形成变量预算，再由场景承接

### 6.1 概率分解

用户明确提出：

\[
P(c)=\sum_vP(v)P(c\mid v)
\]

- \(c\) 是场景。
- \(v\) 是上下文变量。
- \(P(v)\) 是本轮用于响应变量 \(v\) 的预算。
- \(P(c\mid v)\) 是决定响应 \(v\) 后，预算分配给场景 \(c\) 的比例。

原始预算首先根据上下文显著程度形成，场景数量及关联分布均不参与原始变量预算的计算。场景可用性随后按第 6.4 节处理；条件场景分布则至少与候选集、关联情况、当前显著程度及语义项之间的关系有关，也应考虑场景自身关联项之外的上下文信息。

系统追求桌面对上下文变化的响应机会稳定，不要求某个场景固定得到多少概率，也不要求控制最终场景合计覆盖了多少上下文。

### 6.2 预算来源与最终覆盖分别理解

在其他季节关联支持相近、没有明显相反的季节语义影响选择的示意条件下，若天气预算为一半、活动预算为一半，活动内部暂均分前述五个工作场景，而天气预算全部由雨天工作承接，则雨天工作获得：

\[
\frac12+\frac12\times\frac15=60\%
\]

四个季节工作各获得 10%。这些数字仅说明机制，不是默认预算或分配规则。

天气来源预算是 50%，最终天气关联场景覆盖是 60%，多出的部分来自活动预算。稳定量是专门用于响应变量的预算份额，不是强制最终覆盖量等于这份预算。复合场景获得多个来源，不意味着额外创造预算。

### 6.3 场景承接与归一化

记 \(C_v\) 为本轮候选池中关联变量 \(v\)、可承接其预算的场景集合。具体语义关联如何确定该集合，仍待问题三及场景表示讨论。

条件分布满足：

\[
P(c\mid v)=0\quad(c\notin C_v),\qquad
\sum_{c\in C_v}P(c\mid v)=1
\]

每个有效变量的预算分完一次，最终场景分布总和为 1。一个场景可以从多个变量获得预算。属于候选集合也不保证其条件概率为正；第 4.5 节的零概率结果需要在每个正预算来源的条件分配中得到体现。

### 6.4 无候选变量：忽略并按比例归一

用户选择的处理方向是：若 \(C_v\) 为空，忽略该变量的响应预算，将其余变量的预算按比例归一。该变量提供的上下文语义仍可以参与其他变量的条件场景分配。

把不受场景数量影响的原始预算记为 \(P_0(v)\)，并定义：

\[
V_+=\{v:C_v\ne\varnothing\},\qquad
Z=\sum_{u\in V_+}P_0(u)
\]

当 \(Z>0\) 时，本轮有效预算为：

\[
P(v)=
\begin{cases}
P_0(v)/Z,&v\in V_+\\
0,&v\notin V_+
\end{cases}
\]

两个正预算、仍可响应变量的相对比例保持不变。可用性可以排除变量，某个变量拥有更多场景则不会因此提高它的预算。

用户给出的两个解释是：

1. 没有配置对应播单时，可以理解为用户没有对该变量显著时刻的响应期待。
2. 先随机选择响应变量；若它没有候选，重新选择直到落到非空 \(C_v\)。这与忽略后按比例归一的条件分布相同。

若空集来自本轮偏好召回范围，数学处理同样适用，但不必据此推断用户长期没有该变量的期待。

例如第 4.5.2 节的晴朗情形，没有场景可以响应当前晴朗天气，因此天气不获得响应预算；但晴朗语义仍应使雨天工作在活动预算内得到零概率。预算可用性与语义是否参与比较是不同的职责。

\(Z=0\) 时无法按这一步归一，重复选择也无法成功，需要在尽力选择行为中定义退化分布。候选池本身为空时，没有场景可采样；本文不擅自定义执行行为。

### 6.5 显著性门槛与概率跳变

当前讨论中，变量先通过显著性边界，才进入正常的预算分配。因此，预算与最终概率分布可以在边界处跳变。

用户认为这种跳变可以接受：变化首先发生在选择概率中，之后仍需采样，不意味着跨过边界就必须立即切换场景。完整概率连续性不再作为硬要求。

跳变的实际影响还取决于新增变量的预算大小、条件场景分布与原分布的重叠，以及后续采样和状态更新。采样不消除分布变化，但本轮不预设稳定切换的具体机制。

### 6.6 负向影响在条件分配中体现

各个 \(P(c\mid v)\) 都应结合相关上下文的正向支持与负向影响。即使本轮分配的是活动预算，明显的季节或天气仍可以影响工作场景之间的分配。

这样，每个变量保有自己的响应预算，由条件分布选择合适的场景承接。对混合后的最终场景分布统一扣减再全局归一，可能改变各来源实际贡献的预算比例；具体算法仍需遵守先形成变量预算、再由场景承接的方向。

## 7. 三部分行为要求与待定事项

用户明确要求：当前最多细化行为描述，尚未到固化算法的时机，因为问题三仍需解决。第 4.5 节的约束实例已确认；其他早期行为草案保留其待确认状态，具体算法均未定。

### 7.1 变量预算随显著程度变化（待确认的行为草案）

在偏好和可响应资格相同的条件下，更显著的变量应获得更多预算；同等显著时保持对称；其他条件不变时，提高一个变量的显著度不应使其自身预算下降。

“同等显著”“更显著”的跨变量含义，依赖问题三。预算的具体函数、浓淡程度、显著门槛数值，以及与偏好参与范围的最终衔接，均未确定。

### 7.2 条件场景分布

从响应 \(v\) 出发，结合相关上下文比较哪些关联场景更贴切。额外关联有充分支持时，复合场景可以更有优势；支持不足时，更专注于当前变量的场景可以占优。明确相反的关联还可以构成零概率的理由；没有表达某个上下文，不等于与它相反。

雨天与雨天工作，以及第 4.5 节的两组实例，是这一分布需要满足的行为约束。怎样表达语义关系、组合正向支持与负向影响、确定通用的零概率条件、是否使用关联成本，以及如何处理相同关联的多个场景，都未确定。

### 7.3 无显著变量时的尽力选择

此前已确认：没有显著变量时，候选范围是全体可用场景，并进行尽力选择。

助手进一步提出区分“仍有弱上下文信息”和“完全没有可用上下文信息”：前者可利用弱支持，但没有必须响应某一变量的要求；后者需要明确基准选择行为。这一区分及基准分布仍待确认，不能直接写成均匀随机或固定后备场景。

## 8. 问题二仍未定案的部分

- 原始变量预算 \(P_0(v)\) 的具体分布。
- 条件场景分布 \(P(c\mid v)\) 的具体计算。
- 语义项之间的关系如何表达，以及负向抑制与零概率的通用适用范围；第 4.5 节的具体约束实例已确认。
- 无显著变量、可响应预算总和为零及其他无可用上下文情况下的尽力选择。
- 场景关联的正式语义与表示，包括粗变量和具体语义项的关系。
- 显著性边界 \(b\)、可能的场景关联交接点 \(a\) 及其他模型参数；不预设这些参数必须存在于最终算法。
- 采样时机、采样频率、当前场景与历史状态怎样参与选择，以及何时更新系统状态。
- 用户配置偏好的具体交互表达，以及细粒度偏好是否进入产品。

本轮没有设计新运行时接口、持久化模型或实施步骤，也没有把探索模型当成实现契约。

## 9. 下一步：问题三的讨论入口

原问题：

> “当下信息”通常是原始的传感器信息，不具有“场景”层面的语义含义。如何根据这些信息构建场景层面的语义？

问题三需要为前面讨论提供语义地基：当前有哪些语义项、它们怎样由观测支持、什么叫明显或模糊，以及显著程度怎样供预算和场景承接使用。第 4.4、4.5 节还要求语义构建能够支持相关、接近正交与明显相反等关系的判断，具体表示尚未讨论。

已确认的承接边界是：

- 上下文语义独立于用户偏好与 Playlist 内容。
- 天气、活动、时段、季节仍是粗粒度上下文变量；内部语义项怎样构建和表示尚待讨论。
- 显著参照不是最大值，不将边界预先写成 1。
- 语义构建应服务于显著情境的可靠理解，并允许模糊情境中的近似正确。
- 暂不从既有模型、数值窗口或历史参数反推新语义。

助手提出、待用户判断是否需要区分的讨论入口是：

- 信息缺失或无法判断。
- 能判断某个语义当前不存在。
- 某个语义成立，但不显著。

例如“无法判断是否工作”与“能够判断当前没有工作”，未必应为选择模型提供相同的信息。这是待讨论的语义区分，不是已经确定的新状态类型。

下一轮从问题三本身展开，上述待讨论入口不预设讨论顺序。上下文语义的地基明确后，再回到变量预算、条件分布和尽力选择的具体算法。
