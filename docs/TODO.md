# 后续小版本待办

## Open

- [ ] **应用内更新检测**
  - 功能描述：启动后检查 GitHub Releases 的最新版本，有更新时在托盘菜单和设置页提示，也可手动重新检查；点击更新按钮后由应用下载发布包、校验摘要、替换当前程序并重启。
  - 优先级：P1
  - 理由：程序以免安装的单文件 exe 分发，更新入口目前只有 Releases 页面，用户需要自行比对版本号。缺少提示时容易长期停留在旧版本，遇到配置格式变更（如 Profile v4）时也不会提前备份。运行中的单文件 exe 无法就地覆盖，替换方式需要单独确认；离线、代理和 GitHub 限流导致的检查失败应静默降级，不影响使用。

- [ ] **CI 与发布流程**
  - 功能描述：加入 GitHub Actions，把构建、校验和发布从手工改为标签触发：推送和 PR 运行 pytest、Ruff，以及前端类型检查和构建；推送 `v*` 标签时校验 `src/app/version.py`、CHANGELOG 与标签的版本号一致，构建 Windows 发布包并做启动冒烟检查，生成 SHA-256 摘要，用 CHANGELOG 段落生成发布说明并创建 Release。
  - 优先级：P1
  - 理由：GitHub Releases 的版本从 v0.8.3 直接跳到 v0.12.0，0.9 至 0.11 只有事后补打的标签和补记的 CHANGELOG；产物命名也从 `WEScheduler-v0.8.3.zip` 变为 `Tunalo-v0.12.0-windows-x64.zip`。构建、摘要、说明和附件目前全靠手工，版本号与产物容易不同步。固定的产物命名和每个版本都有 Release 也是更新检测的前提；e2e 是否纳入流水线按其耗时决定。

- [ ] **开机启动开关**
  - 功能描述：在设置页和托盘菜单提供开机启动开关，写入或移除当前用户的 Windows 启动项；开机启动后沿用现在的静默进托盘，不弹窗口。
  - 优先级：P2
  - 理由：方便用户选择是否开机启动，避免手动添加或删除启动项。

- [ ] **多显示器支持**
  - 功能描述：针对多显示器下的典型使用场景进行调研，对应分析调度设计和组织。
  - 优先级：P1
  - 理由：系统现有设计针对单显示器，而现在多显示器的需求逐渐增长。此外，多显示器用户有更多机会看到桌面，因此是有价值的 feature。需要对多显示器的使用场景进行调研。举例来说，需要知道"复制单个壁纸"、“拉伸单个壁纸”、“不同显示器的壁纸”的行为差异，如何区分，以及如何让调度器在多显示器下更好地工作。

- [ ] **评估多屏共同调度**
  - 功能描述：沿用现有场景和偏好，让多块屏幕共同呈现当下情境；研究保留各屏原有选择概率的协同选择方式。
  - 优先级：P1
  - 理由：同上

- [ ] **利用更多天气观测字段**
  - 功能描述：评估降雨降雪量、云量等是否能改善显著度，以及季节判断是否需要加入温度。当前天气判断只使用 Open-Meteo 天气代码归类后的天气类型。
  - 优先级：P2
  - 理由：后续评估更多字段对季节、时段、天气显著度的实际收益。

- [ ] **评估独立音频响应语义**
  - 功能描述：当前音频不参与工作／娱乐判断。先判断是否有值得响应、可关联到场景的音频情境，再决定采集什么、如何表达。
  - 优先级：P3
  - 理由：工程量中小，但是需要评估这一块的需求。

- [ ] **重构日志与历史记录**
  - 功能描述：梳理运行日志、动作事件和 Tick History 的职责与数据传递，减少仅为填充记录字段而增加的多层属性转发。记录侧继续消费调度结果。
  - 优先级：P2
  - 理由：需要评估现有日志、记录的价值和必要性
