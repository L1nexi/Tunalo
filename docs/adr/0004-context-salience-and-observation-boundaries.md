# 用观测和有限活动轨迹构建独立的有符号显著度

场景选择需要知道雨、工作、白天、夏季分别有多明显，旧方向归一化和 Policy 权重会混合现实判断与响应偏好。决定由 Policy 从观测及必要轨迹构建每项有符号显著度，保留绝对大小，再交给 [ADR-0003](0003-scene-probability-budgets-and-preference-cascade.md) 的概率模型；语义不因偏好、启用场景、播单或播放状态改变。

## 共同标尺与构建边界

四个变量共用 14 个语义项：四季、`dawn/day/sunset/night`、晴朗／阴天／雨／雪，以及 `focus/chill` 表示的工作／娱乐。正值是支持，零是中性或无证据，负值是反向或违和。负向依据明确违和，不因分类不同就机械地互相排斥；同等明确的通常正向状态以 1 为共同参照，它不是上限，暴雨等更强状态可以超过 1。

构建先锚定感知明确的状态，再近似中间区域，显著边界不反过来塑造曲线。支持依据增强时显著度不下降，也不因状态持续、用户可能习惯而自动减弱。判断把握和显著程度不是同一概念，当前不另增统一的置信度维度。缺失观测沿用已有零证据和缓存回退，不额外建立一套统一缺失状态分类。

共用的幅度映射为三次幂指数曲线：

$$
f_q(z)=\frac{1-2^{-(z/q)^3}}{1-2^{-(1/q)^3}},\qquad 0\le z\le1,\ q>0
$$

它保持零点、端点及单调性；各变量共用函数结构而不强制共享参数。活动使用有符号扩展 `F_q(r)=sgn(r)*f_q(abs(r))`；周期过渡用 `v_a+(v_b-v_a)*f_q(u)` 连接锚点。天气强度直接按观测映射，不经过该函数统一封顶。采用同一函数族并不代表跨变量体验校准已经完成。

## 活动：前台轨迹、固定槽位与净方向

只用前台应用身份、窗口标题及其近期分类轨迹判断工作或娱乐。完整桌面窗口池、普通后台进程、输入频率、媒体播放和系统会话未显示足够的独立收益，当前不加入活动主线。无输入可以是阅读或思考；有音频也不证明注意力。界面内容读取、截图和识别的投入与观察边界不适合当前目标。

每次现有采样推进一个槽位，保存最近 600 次分类观察，约对应十分钟；它取代早期讨论中的三十分钟时间窗。年龄按最新为 0、最旧为 599 的槽位次序计量，不按实际采样间隔重采样，也不在停止或休眠后补槽。固定槽位复用原轮询，避免为近似活动判断引入另一套采集时钟。

以工作为正，工作／娱乐／OTHER 的方向分别是 `1/-1/0`，年龄权重及净方向为：

$$
w(a)=2^{-(a/h)^3},\qquad
r=\frac{\sum_{a=0}^{599}w(a)x_a}{\sum_{a=0}^{599}w(a)}
$$

未观察槽和 OTHER 均按零参加全窗口分母，不按已识别数量重新归一。先合成支持与反向证据，再输出 `s_focus=F_q(r)`、`s_chill=-s_focus`；不能先逐段非线性映射再求和。一次明确观察不会成为满值；连续 600 次同方向覆盖整个窗口时达到 1。时间权重只看年龄，不叠加连续段奖励、短暂穿插状态或独立等待阈值。

用户活动规则只决定窗口如何被分类，不开放活动曲线或匹配数值。最终保留自定义进程与标题规则：未提供活动配置时使用产品默认规则；显式配置完全替换默认，空对象不识别活动，不合并两套规则。标题优先于进程，识别器保留已有匹配优先级与标准化。初步实施时删除用户规则的方案已撤回。

轨迹只保存工作／娱乐／OTHER 分类，不保存窗口标题和 Context 历史。OTHER 不表示空闲，不是可关联语义项，也不另建游移显著度。暂停仍采集，停止不采集，同一运行实例恢复可继续使用内存轨迹，进程重启从零开始；状态所有权与热替换见 [ADR-0005](0005-selection-and-scheduling-boundary.md)。

## 季节与时段：平台和真实昼夜锚点

季节只使用当地日期，沿用年内日期与 365 日周期。每个季节的本位峰值附近为 1，相对季节为 -1，相邻季节为 0；四个季节各有峰值前后十日的平台，平台之间 S 形过渡并跨年闭合。暂不把气温或日照融合成季节，邻季也不机械地达到负向排除程度。

时段沿用天气 API 的日出、日落和昼夜中点，保留 `dawn/day/sunset/night`。把相邻真实峰值之间映射为六个虚拟小时，再用 `1/0/-1` 锚点直接 S 形连接；真实峰值间距随昼夜长度变化，时段不设平台。该决定覆盖早期固定钟点与时段平台构想。没有获得过有效日出日落时全零；本次缺数据而已有峰值时保留既有值，不另加固定钟点兜底。

## 天气：共享晴朗、阴天与降水关系

OWM 代码提供正向依据，Policy 统一推导晴朗、阴天、雨、雪的支持和反向关系。阴天表达没有降水、也不明显晴朗，不能因雨天云多就重复支持阴天。降水是雨雪的共同推导概念，不另成为预算来源。

- 晴朗与明显降水强反向；阴天与二者弱反向。
- 雨雪各保留自己的正向强度，混合时公共降水强度取 max，不重复增强对晴朗与阴天的反向证据。
- 降水对晴朗的强反向随强度变化，对阴天保持弱反向；初步实施将晴朗、阴云全部设零的方案已撤回。

降雨沿用小雨／中雨／大雨／暴雨约为 `0.25/0.5/1/2` 的共同标尺，逐代码允许中间值及超过 1 的强度。数值是内部感知校准，不是 API 返回的显著度，也不宣称天气代码对应某一毫米降水阈值。当前使用代码、主分类和日出日落，不新增降水量、云量或额外请求。

已知代码优先，即使结果全零也不按主分类重新解释；只有未知代码才回退主分类。没有观测或两者均未知时全零；请求失败继续解释已有 Sensor 缓存。具体公式、代码强度和默认值属于实现维护，见[开发指引](../DEVELOPMENT.md#天气共同推导)及 [WeatherPolicy](../../core/policies/weather.py)。
