# 产品定位与开发指引

状态：持续维护。本文件面向开发阶段，描述产品希望长期实现的体验和取舍原则；具体功能是否已经交付，以代码、测试和当前验收记录为准。用户入口的介绍见根目录 `README.md`。

## 核心定位

本项目是一款面向 Windows 上 Wallpaper Engine 用户的场景调度工具。用户用自己的播放列表表达不同情境下想看到的画面；调度器感知当下、选择合适的场景并安排切换，使桌面氛围与现实生活相呼应。

“呼应”不等于机械地复现环境。下雨时选择雨景，冬天选择雪景或温暖的炉火，都是用户对情境的审美解释。产品负责判断情境和执行调度，不替用户决定哪一种画面才正确。

## 目标用户与要解决的问题

目标用户已有较多 Wallpaper Engine 壁纸收藏，能明显感受到原生定时、按时段或按星期切换的局限。他们希望在不同情境下看到不同风格的壁纸，也希望桌面与天气、季节、昼夜和自己的活动产生联系。

对这类用户，壁纸是日常可见的桌面内容。单一的大播放列表可能让白天与夜晚的观感失配；只使用少量固定壁纸则难以展示收藏。机械地按点切换还可能打断游戏、全屏工作或正在进行的操作。本项目要让已有收藏更适时地出现，同时让切换时机服从实际使用状态。

## 产品如何工作

1. **用户定义画面。** 产品提供可理解的预设场景。用户选择要启用的场景，并将每个场景关联到自己在 Wallpaper Engine 中整理的播放列表；多个场景可以关联同一个播放列表。播放列表内包含哪些壁纸，由用户决定。
2. **调度器判断情境。** 时间与日出日落、季节、天气，以及由用户设置的工作或休闲活动规则，共同参与场景匹配。用户通过面向体验的偏好表达响应风格；具体匹配权重和阈值由产品负责。
3. **场景先于播放列表。** 匹配结果可以是场景池。当候选场景的相似度足够接近，调度器将它们视为当前无法有效区分的选择；执行时，各候选场景按其关联播放列表的壁纸数量贡献抽取权重。同一播放列表由多个候选场景关联时，各场景分别贡献权重。这是展示收藏的既定调度语义，不应把池内微小分差重新当作强弱排序。
4. **调度器安排时机。** 场景变化与壁纸轮换都要考虑启动等待、空闲、全屏、设备负载及相应的时间限制。用户可以暂停、恢复或主动要求应用当前匹配。情境匹配和实际切换是两个决策，不以即时切换作为“呼应”的定义。
5. **Wallpaper Engine 执行播放。** 本项目接管场景选择和调度流程，沿用 Wallpaper Engine 保存并播放用户的壁纸收藏。用户在 Wallpaper Engine 中手动切换后，调度器读取实际播放列表：已关联的播放列表用于恢复活跃场景身份，未关联的播放列表由恢复流程处理；手动切换不会永久移交调度控制权。

## 开发阶段的判断准则

- **保留用户的审美主导权。** 场景表达何时适合一类画面，场景到播放列表的关联表达用户希望呈现什么。不能从场景名称推断播放列表内的具体视觉内容，也不能承诺自动保证某种亮度或观感。
- **保留场景的语义身份。** 场景和播放列表不是同一个概念。即使多个场景指向同一播放列表，它们在匹配、跨次调度记忆和连续性判断中仍有各自的身份。术语以根目录 `CONTEXT.md` 为准。
- **尊重已确定的模糊情境处理。** 场景池用于处理匹配分数接近、无法可靠判定单一赢家的情境。池内按壁纸数量选择是有意的取舍。只有出现具体、可复现的体验问题，才重新评估这一规则；不能单凭“分数略高却未多获抽取机会”认定它失效。
- **让设置表达使用意图。** 用户需要理解并控制场景关联、响应风格和打扰程度；内部标签、单项策略权重与匹配阈值由产品维护，不要求用户理解算法才能完成设置。
- **优先检验真实情境。** 预设场景长期由产品定义，不开放任意自定义。现有场景没有覆盖情境维度的全部组合；扩充场景或调整匹配时，应先提出具体的错误结果与期望结果，再验证改动对其他情境和切换稳定性的影响。

## 长期边界

播放列表是目前适合本产品的画面选择粒度。图像聚类、单张壁纸识别或反馈系统可以作为进一步探索，但不能代替用户对壁纸的审美判断；若引入此类辅助能力，用户必须能够参与、校正并决定结果。

产品定位仍以 Windows 上的 Wallpaper Engine 增强为基础。对外介绍应以实际交付的能力为准，不把上述探索写成现有功能，也不宣称实时天气响应、自动理解每张壁纸或绝对不打扰的切换。
